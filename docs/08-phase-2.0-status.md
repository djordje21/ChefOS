# ChefOS — Phase 2.0 Status (14 Oct 2026)

Phase 2.0 hardened security and added E2E testing. Phase 2.1 added the costing engine as an isolated module. Nothing is deployed, and no production credentials were used.

## Part A — Security hardening

| Finding | Fix | Regression tests |
|---|---|---|
| **H1** An invitation outlived its sender's authority | `accept_invitation` re-checks that the sender is still an active member of an active workspace with `member.manage`, holds every permission of the invited role, has all-outlet access if the invitation grants it, and holds every granted outlet permission. Open invitations are revoked automatically when the sender's role, outlet access or membership changes (`revoked_reason`). The preview shows `invalid` when an invitation can no longer be honoured | `tests/db/hardening.test.ts`: sender demoted, loses `member.manage`, removed, leaves, suspended, loses all-outlet access, loses the granted outlet permission, role permission removed directly (accept-time check); control cases for a valid invitation and for unrelated changes; revocation reasons |
| **M1** Acceptance into a suspended workspace | Refused. The invitation stays usable once the workspace is reactivated | Suspended → rejected, nothing written; reactivated → accepted; no invitations can be created while suspended |
| **M2** Deactivated outlets left access in place | A deactivated outlet grants **no** outlet permission to anyone, including all-outlet members. Only `outlet.manage` still sees it, in order to reactivate it. No new access can be granted on it, and open invitations to it are revoked. Assignments are kept and apply again after reactivation | Restricted and all-outlet members lose access; managers still see it; grants and invitations are refused; only invitations to that outlet are revoked; access returns after reactivation; a restricted manager loses the ability to grant it |
| **E2E bug found** (not in the audit) | After email confirmation, redirects were built from the server's own origin (`localhost`) while the browser used `127.0.0.1`. The fresh session cookie therefore did not apply and the user landed back on sign-in. Route handlers now use relative redirects and the proxy uses the Host the browser sent | Playwright E2E; `tests/unit/redirect.test.ts` |

**Database change:** one additive migration, `supabase/migrations/20261014000100_security_hardening.sql`. It adds the column `invitations.revoked_reason` and new or replaced functions and triggers. Nothing is dropped and no data is changed.

**Mutation check:** `scripts/security-mutation-check.sh` has 4 new sabotages. All **12/12** are detected:
- the sender re-check removed;
- the auto-revoke trigger dropped;
- the suspended-workspace check removed;
- the active-outlet condition removed.

**E2E:** `e2e/auth-workspace.spec.ts` (Playwright) runs against the local Supabase stack and its mail catcher. It covers:
- private routes redirect to sign-in;
- sign-up, then sign-in is refused before confirmation, then the emailed link confirms and signs in;
- a new user has no workspace; workspace and outlet creation;
- sign-out, private route blocked, sign-in returns to the page the user was on, data persists;
- an invitation with outlet restriction: the invitee signs up, accepts, and sees only their outlet;
- the invitation link is single-use;
- a foreign workspace URL gives 404.

**Generated types:** `src/lib/supabase/database.types.ts` is generated by the Supabase CLI (pinned to 2.120.0) from the local stack and used by the server clients. CI fails if the file differs from the migrations. To regenerate: `npm run db:types`.

**RLS:** existing policies are unchanged apart from the outlet-activity condition, which is covered by the tests above and the full isolation suite. Optimising RLS performance is deferred to the high-volume tables in Phase 2.2.

## Part B — Costing engine

See `09-costing-engine.md`. The engine lives in `src/lib/costing/`, built on decimal.js and zod-validated versioned policies. It has no constants or defaults, works on fictional test data, and is not connected to the database or the UI.

## Remaining risks and open items

* **Hosted Supabase is not configured or verified.** Production auth settings (email confirmation, password policy, SMTP, CAPTCHA) are dashboard settings, listed in `docs/06`.
* **E2E does not cover:** password reset, role changes and member removal through the UI, or the audit page.
* **Account deletion is blocked by foreign keys (M3), and there is no CSP header (M4).** Both still open; neither affects Phase 2.2.
* `set_outlet_access` takes `NULL` to remove access, but the generated types mark the argument non-null, so the call site casts it, with a comment.
* Supabase CLI warns that the config section `[inbucket]` is deprecated (renamed `[local_smtp]`). It still works; rename it when the CLI is next upgraded.
* GitHub warns that the pinned actions use Node 20, which is deprecated. Bump the action versions.
* Repository visibility and the superseded commits still on GitHub remain the owner's decision (see the earlier history-rewrite report).
